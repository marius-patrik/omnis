# Omnis v0 Nix Control and Provenance Contract

**Status: NORMATIVE.** This document freezes the exact Nix/NixOS boundary used by OmnisManager and
OmnisOS. Nix remains deterministic and model-free. Implementation agents do not choose an alternate
evaluation path, text parser, provenance representation, store observer, or candidate-build flow.

Canonical sources:

```text
protocol/nix_control.capnp
spec/nix_control.toml
```

## 1. Two deterministic surfaces

The Nix fork exposes two different surfaces because evaluation and privileged store mutation have
different lifetimes/authority.

### 1.1 Store/control surface

The patched `nix-daemon` retains its normal upstream protocol unchanged and additionally listens on:

```text
/run/omnis/nix-control.sock
```

The socket is Unix `SOCK_STREAM`, Cap'n Proto RPC, owner `root:omnis`, mode `0660`.

It exposes exactly `NixStoreControl` from `protocol/nix_control.capnp`:
- path/derivation metadata;
- closure;
- realization plan;
- realization;
- GC plan;
- exact-path GC execution;
- full store/root snapshot;
- store/build lifecycle subscription.

No evaluator runs inside nix-daemon and no model code links into Nix.

### 1.2 Evaluation surface

System evaluation runs in the companion C++ binary `omnis-nix-eval` built from the same pinned
OmnisManager/Nix source tree.

Manager starts one process per EvaluationId and passes one Unix `SOCK_STREAM` socketpair endpoint as
fd 3. Cap'n Proto RPC over fd 3 exposes `NixEvalService`. stdin/stdout/stderr are not an API.

The helper exits after its EvaluationStream is drained/cancelled. It has:
- read-only access to the pinned nixpkgs store path, `/etc/omnis/base.nix`, and the candidate dir;
- Nix daemon access for store queries;
- no network;
- `LANG=C.UTF-8`;
- `TZ=UTC`;
- no model/provider/harness credentials.

## 2. Canonical machine configuration files

v0 uses exactly:

```text
/etc/omnis/base.nix
/etc/omnis/managed.nix
/etc/omnis/configuration.nix
```

Ownership:
- `base.nix`: user/admin-owned NixOS module. Omnis never rewrites it.
- `managed.nix`: fully generated from Omnis system graph state. Users do not edit it.
- `configuration.nix`: Omnis-owned stable wrapper.

The wrapper content is semantically exactly:

```nix
{ ... }: {
  imports = [
    /etc/omnis/base.nix
    /etc/omnis/managed.nix
  ];
}
```

Formatting is generated by the Nix AST printer; string substitution/regex editing is forbidden.

The initial installer creates `base.nix`; hardware/user custom modules are imported from there.

## 3. Candidate evaluation

For GenerationId G:

```text
/var/lib/omnis/candidates/<G>/
  managed.nix
  configuration.nix
  evaluation/
  build/
```

Candidate `configuration.nix` imports the same absolute `/etc/omnis/base.nix` plus its sibling
`./managed.nix`. Evaluation never edits the active files.

Manager sends:

```text
EvaluateSystemRequest
  evaluationId
  exact pinned nixpkgs store path
  baseModule=/etc/omnis/base.nix
  managedModule=/var/lib/omnis/candidates/<G>/managed.nix
  system=<host Nix system string>
  TraceContext
```

`omnis-nix-eval` evaluates the pinned nixpkgs NixOS `lib/eval-config.nix` with exactly those two
modules and no `NIX_PATH`/environment source lookup. Evaluation is pure. If a module requires an
unrealized impure fetch, evaluation fails; Manager does not enable network as a fallback.

## 4. Option provenance

Pinned nixpkgs already publishes option metadata from `lib/modules.nix`, including
`declarationPositions`, `definitionsWithLocations`, `highestPrio`, `valueMeta`, type metadata
and final value. Omnis consumes those fields; it does not reimplement module merging.

Each declared option becomes one `OptionRecord`, ordered by option path UTF-8 bytes.

Definitions are the final contributing definitions from `definitionsWithLocations`, in their
post-`mkOverride`/post-`mkOrder` merge order. Each records:
- source file/optional line/column;
- BLAKE3 of the raw source file bytes;
- zero-based final order;
- the option's `highestPrio`;
- deterministic value fingerprint.

Declarations come from `declarationPositions` and preserve list order.

`mergeApi` is:
- `v2` when the option type's merge has `v2`;
- `legacy` otherwise.

Suppressed lower-priority definitions are not called contributors. Their source remains discoverable
from module source; v0 explain answers why the **final** value exists, not a hypothetical alternate
merge.

## 5. Option value fingerprint

First try to force `builtins.toJSON option.value`.

On success:
- encoding = `json`;
- JSON bytes are the exact UTF-8 result from pinned Nix;
- digest = BLAKE3(JSON bytes);
- store-path string contexts are extracted, deduplicated and UTF-8-byte sorted.

If JSON conversion cannot represent the final value:
- encoding is `opaque-function` for functions, otherwise `opaque-external`;
- digest input is the NUL-delimited concatenation:
  `encoding`, option type name, each declaration source tuple, each contributing source-file
  BLAKE3, and each contributing definition fingerprint;
- the final BLAKE3-256 is the ValueFingerprint digest;
- JSON is absent.

A source tuple serializes as UTF-8 file path, decimal line or empty, decimal column or empty.

This fallback is for diff identity/provenance, not value reconstruction.

## 6. Evaluator trace

The OmnisManager fork instruments `EvalState::forceValue` only while `omnis-nix-eval` has an
active evaluation trace.

Each forced expression with a valid source position emits:

```text
EvalTraceRecord
  monotonically increasing id starting at 1
  parent id (0 = evaluation root)
  file/line/column
  expression kind
```

Parent is the currently forcing expression on the evaluator's thread-local force stack.

Records stream immediately through `EvaluationStream`; the helper does not accumulate the full DAG
in RAM. Manager writes the ordered records to a CAS artifact and records that ArtifactId on the
Generation/Evaluation provenance.

Expressions without source positions are still evaluated normally but do not create trace nodes.
The trace cannot change evaluation semantics.

## 7. Derivation/store records

`StorePathInfo` is sourced from Nix store path info. Reference lists are UTF-8-byte sorted.
`DerivationInfo` is sourced from parsed derivations; input derivations and sources are sorted by
store-path bytes, output names by UTF-8 bytes, args preserve order.

The environment map is serialized as canonical JSON with keys sorted by UTF-8 bytes and stored as a
protected/local ArtifactRef; it is not copied into Agent context by default because derivation
environments can contain large/sensitive material.

## 8. Realization planning

`planRealization` snapshots the current store validity and configured substituter availability.

Every required path is classified exactly:
- `alreadyValid` if valid locally;
- `substitute` if Nix reports an available valid substitute at plan time;
- `build` otherwise.

The plan contains the complete transitive realization closure. Order is dependency-topological; ties
use store-path UTF-8 byte order. Totals sum the plan-time download/NAR sizes reported by Nix.

Plan state is evidence, not a promise: availability can change before realization. `realize`
returns the actual final plan classification/evidence after completion.

Only upstream Nix build mode `normal` is used in v0.

## 9. Store observer

Each nix-daemon start allocates a UUIDv7 `daemonBootId`; event sequence starts at 1.

The control surface keeps the newest 100000 `StoreEvent` records in memory. Events cover:
- build start/completion;
- substitution;
- path registration/deletion;
- GC start/completion.

If Manager reconnects with a different boot ID or an unavailable sequence, subscription returns a
Conflict requiring `snapshot()` before resubscription.

Snapshot streams:
1. all valid store paths sorted by store-path bytes;
2. all GC roots sorted by root path bytes.

Manager reconciles Resources/derivations/realizations into the shared graph and emits ordinary graph
transactions/events. Nix observer records themselves are deterministic physical evidence, not a
second semantic graph.

Normal non-Omnis Nix client operations are observed too. Their TraceContext gets:
- UUIDv7 RequestId/TraceId allocated by nix-daemon;
- actor mapped from peer UID;
- no causal parents.

Omnis-originated control calls preserve the supplied TraceContext.

## 10. GC

`planGc` receives the complete root set assembled by Manager under the retention policy. Nix computes
the unreachable set; returned candidates are store-path-byte sorted.

`gc` accepts the exact candidate path list from the previously surfaced plan and deletes only those
paths that remain unreachable. If reachability changed, Nix skips the now-live path and reports it as
not deleted; it never expands deletion beyond the request.

Manager records planned and actual deletion sets.

## 11. System diff

Manager compares active Evaluation A and candidate Evaluation B deterministically.

Option diff:
- union option paths, UTF-8 sorted;
- added/removed/changed by final ValueFingerprint digest.

Derivation diff:
- compare system derivation paths and recursively compare derivation input/output records.

Closure diff:
- set difference of store closures;
- added/removed paths sorted by store-path bytes;
- aggregate NAR/download sizes from StorePathInfo/plan.

Service impact:
- compare the canonical systemd unit derivation/resource graph produced by the NixOS generation;
- unit names sorted lexically;
- classify `added|removed|restart|reload|unchanged` from NixOS switch metadata;
- omit `unchanged` from the rendered diff artifact but retain it in the typed internal result.

Semantic diff:
- map changed options and realized Resources to shared graph identities;
- no model call participates.

All four diff forms are serialized as Cap'n Proto-derived canonical artifacts and attached to
GenerationDiff.

## 12. Build and activation split

Nix control can evaluate/plan/realize. OmnisOS owns system activation.

Exact generation flow:
1. Manager creates candidate files.
2. evaluator returns candidate system derivation/toplevel + provenance stream.
3. Manager asks store control for realization plan.
4. Manager realizes the candidate closure through Nix.
5. Manager constructs GenerationDiff.
6. OmnisOS runs deterministic preflight invariants.
7. OmnisOS invokes candidate `switch-to-configuration switch`.
8. OS reconciliation verifies required state for 30 seconds.
9. failure invokes previous generation's switch script.
10. only successful activation atomically promotes candidate `managed.nix`.

Neither `omnis-nix-eval` nor nix-daemon activates the running system.

## 13. Hard failure rules

The implementation returns `SpecificationDefect` rather than inventing behavior when:
- a promised option provenance field is absent from the pinned module-system result;
- a store/control operation cannot be represented by `nix_control.capnp`;
- a candidate needs impure/network evaluation;
- a diff cannot preserve exact store/option identities.

Text scraping of `nix-env`, `nix-store`, `nixos-rebuild`, evaluator diagnostics, or
`nix store diff-closures` output is not a v0 implementation path.
